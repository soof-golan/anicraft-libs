# Working on the AniCraft family (anicraft-libs, anicraft, charcraft)

These rules apply to every crate in the three repositories. They combine the namtao.com/rust strict lints, the
conventions of the storytold Craft apps (PhotoCraft, VectorCraft, EffectCraft, FilmCraft) and the project owner's
own rules. CI enforces most of them.

## Clean room

- Behaviour only, from public specs and our own observation of files we are allowed to read. Never copy code,
  shaders, icons, fonts, sample files or other assets from Adobe products, and never decompile Adobe binaries.
- Reverse engineering of file formats is for interoperability only and is done from sample files. Sample files
  from users are never committed (they live outside the repo; tests that need them read `ANICRAFT_SAMPLES` and are
  skipped when it is unset). Committed fixtures are generated by our own code or written by hand.
- Code reused from the Craft repos (MIT OR Apache-2.0) is fine: depend on the crate by git rev, or copy a module
  with its notice and add a row to `ATTRIBUTION.md` in the same commit.

## Code rules

- No panics outside tests: `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, indexing and
  slicing (`v[i]`, `&s[a..b]`), unchecked integer arithmetic and `as` casts are denied by clippy. Use `get`,
  `checked_*`/`saturating_*`, `try_from`, iterators, and `?` with typed errors. Inside `#[cfg(test)]` they are
  allowed.
- Treat every file as hostile input: bound recursion depth, cap allocations, never trust lengths and offsets.
  Every crash fix gets a regression test.
- No `unsafe` in our crates (`unsafe_code = "forbid"`). Dependencies may use it.
- No shared mutable state: no `Arc`, `Mutex`, `RwLock`, `Rc`, `RefCell` (clippy `disallowed-types`). Background work
  runs in an actor (a thread or task that owns its state) and talks to the UI over channels (`std::sync::mpsc` or
  `crossbeam-channel`). If a dependency's API forces one of these types on you, confine it to the smallest scope with
  `#[expect(clippy::disallowed_types, reason = "...")]`.
- UI is a pure function of state: `ui(&State) -> Vec<Command>`. Event handlers translate input into commands at
  once; state changes only by applying commands; undo is a snapshot of the document model. Never read widget or
  DOM state back later.
- Don't invent serialization. Plain `serde` derives with `serde_json` (human readable) or `postcard` (binary). Custom
  readers and writers exist only for foreign formats we must be compatible with (XFL, SWF, PSD, CA projects...).
- Libraries return `thiserror` errors; binaries use `color-eyre` (or `anyhow`) at the edge.
- Prefer crates from blessed.rs and the Craft repos. Ask in your report before adding anything else, unless there is
  no blessed option for the job (then say why in the commit message).
- Times are `anim_core::Tick` (re-exported from `filmcraft-time`: i64 at 254 016 000 000 per second, the Craft
  convention) or frame indices; never `f32` seconds in models.
- Text must support right-to-left scripts (Hebrew, Arabic) and bidi mixing everywhere text is shaped, edited or
  exported.
- Small crates: one responsibility each, so they compile in parallel and agents don't collide.
- Must build and run on macOS, Windows and Linux. Use `std::path`, never hard-coded separators; no shelling out to
  platform tools; gate platform code with `cfg` and keep a working fallback.

## Tests

- Unit tests next to the code, integration tests in `tests/`. Round-trip tests for every format (`read(write(x)) == x`)
  and golden tests for rendering (small PNGs, compared with a tolerance).
- Run builds through the queue (see below) in the dev profile. Use release only for benchmarks.

## Visual verification: predict, render, inspect

Passing tests is not enough for anything that draws, deforms or lays out. Every component that produces pixels or
geometry (shapes, rendering, text, timeline, morphs, export, video, file readers, puppets, behaviours) goes through
this loop before its work counts as done:

1. **Design hard synthetic inputs.** Write small files or models by hand in `tests/fixtures/visual/`, each aimed at
   one way the component could go wrong. Examples: self-intersecting and even-odd fills, zero-length segments, hairline
   and huge strokes, joins at near-180° angles, gradients with stops out of order, nested symbols with
   scale/skew/rotation, masks inside masks, alpha and colour transforms that combine, mixed RTL/LTR text with
   numbers and line breaks inside a run, tweens across rotation wrap-around, puppets with heads, limbs and draggers
   pushed to extremes. Every fixture is original and synthetic; never derive one from the Adobe samples.
2. **Write the prediction first.** Before rendering, write down in `tests/fixtures/visual/<name>.expect.md` what the
   output must look like: specific pixel colours at named coordinates, which regions are filled and which are holes,
   where edges fall (to the pixel), text order and caret positions, what stays connected. Derive it from the format's
   rules, not from the current output.
3. **Render and inspect closely.** Render to PNG under `/mnt/data/anim/scratch/visual/<crate>/`. Open every image with
   the Read tool and compare it to the prediction region by region, zooming in with crops of the detailed areas
   (edges, joins, neck/attach points, glyph clusters). Write the verdict for each point in the `.expect.md`.
4. **Fix the code.** When the render disagrees with a correct prediction, fix the code. Do not edit the prediction to
   match the output. If the prediction was wrong, explain why in the `.expect.md` before changing it.
5. **Lock it in.** Turn the checked points into assertions (pixel probes with a tolerance, geometry checks), and keep
   the PNG as a golden for that fixture. Copy one representative image per crate to `/mnt/data/anim/scratch/screenshots/`.

## Building: always through the job queue

Never run `cargo` directly for builds, checks, clippy or tests. Use the queue so parallel agents share the machine:

    /mnt/data/anim/tools/q -p <priority> -- mbx clippy -p <crate> --all-targets -- -D warnings
    /mnt/data/anim/tools/q -p <priority> -- mbx test -p <crate>
    /mnt/data/anim/tools/q -g heavy -p <priority> -- mbx build -p <app>        # full app links, packaging

`mbx` wraps cargo with a shared compile cache. Cheap commands (`cargo metadata`, `cargo fmt`, `git`) run directly.
Before landing, also check that the crate compiles for the other platforms:

    /mnt/data/anim/tools/q -p <priority> -- mbx check -p <crate> --target x86_64-pc-windows-msvc
    /mnt/data/anim/tools/q -p <priority> -- mbx check -p <crate> --target aarch64-apple-darwin

(Crates with C build scripts may fail to cross-check for lack of a C toolchain; say so in your report instead.)

## Editing and landing

- Create and modify files only with the Edit and Write tools, never with shell redirection, `sed`, `cat <<EOF`,
  scripts or `cp`. `cargo fmt` is allowed.
- Work in your own git worktree on your own branch.
- Commit often, in small atomic commits (one logical change each, tests passing), with Conventional Commit messages:
  `feat(anim-scene): add symbol instances`, `fix(anicraft-xfl): tolerate short central directory`,
  `test(...)`, `refactor(...)`, `docs(...)`, `build(...)`, `ci(...)`, `chore(...)`. The scope is the crate name.
  Never add Co-Authored-By or any other AI attribution to commits.
- Land with `/mnt/data/anim/tools/land -p <priority> -- <check command>`: it rebases on `origin/main`, re-runs your
  check through the queue and pushes straight to `main`. There are no pull requests.
- Only touch your own crate's directory unless your task says otherwise. Adding a dependency to the root
  `[workspace.dependencies]` is fine.
